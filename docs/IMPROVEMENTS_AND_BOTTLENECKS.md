# Улучшения и узкие места

Версия документа: 1.4.0. Дата: 06.10.2026. Получение данных бесплатно. Реализована предварительная 0.7.0; здесь указаны проверенные меры и фактические ограничения.

## Основные риски

| Риск | Последствие | Как обнаружить | Что делать | Приоритет |
|---|---|---|---|---|
| Неполный охват мирового футбола | Матчи отсутствуют незаметно | Сверка реестра лиг/сезонов, missing-results ratio | Подтверждать покрытие отдельно для расписания и итогов; подключать дополнительные источники | P0 |
| Квоты и пиковые игровые дни | Итоги приходят поздно | Остаток бюджета, 429, возраст очереди | Пакетные запросы, общий лимитер, приоритет итогов, адаптивные интервалы | P0 |
| Нет точного времени окончания | Невозможно обеспечить точные 72 часа от фактического конца | Доля anchor=observed | Использовать первое подтверждение и явно показывать погрешность; выбрать источник с временем конца | P0 |
| Повторный сбор удалённого матча | Нарушение retention | Тест повторного импорта после очистки | Фильтр по окончанию и минимальные маркеры удаления с TTL | P0 |
| Переносы и прерванные игры | Ошибочное завершение или потеря матча | Возраст unresolved, смена kickoff/status | Не считать время начала доказательством конца; продолжать контролируемый опрос | P0 |

| Ошибочное сопоставление источников | Смешиваются команды и результаты | Конфликты ID, необычные смены команд | Таблицы соответствий, provenance, ручная проверка неоднозначностей | P1 |
| Поздний старый ответ | Новый результат перезаписывается старым | source_updated_at и история конфликтов | Проверять версию, сериализовать обновления одного матча | P1 |
| Падение worker и зависшие задания | Обновления прекращаются | Возраст lease и due jobs | Lease, идемпотентность, безопасное повторение, heartbeat worker | P0 |
| Часовые пояса и переход даты | Запрос не того дня | Тесты UTC/DST и границ диапазона | Хранить UTC, переводить даты при построении запроса адаптера | P1 |
| Недоступность источника/доступа | Частичный или полный простой | Ошибки 401/403, circuit breaker | Проверить доступ; резервный разрешённый источник; показать stale-данные | P0 |
| Массовая очистка | Блокировки БД и медленный API | Lock wait, длительность cleanup, p95 чтения | Индекс expires_at, удаление небольшими пачками; не выполнять огромную транзакцию | P1 |
| Кэши, выгрузки и бэкапы | Матчи остаются после срока | Проверка всех копий данных | TTL кэша до expires_at, каскадное удаление, согласованная политика копий | P0 |
| Логи/payload растут быстрее БД | Заполняется диск | Размер диска, скорость роста | Ротация, ограниченные payload, агрегированные метрики | P1 |

P0 — закрыть до стабильного запуска; P1 — проверить до расширения нагрузки; P2 — улучшение после накопления измерений.

## Расчёт бюджета запросов

Для отдельного опроса матчей приблизительно:

```text
requests_per_day ≈ leagues × schedule_polls_per_day
                 + sum(active_matches_per_interval × polls_in_interval)
                 + final_rechecks + discovery + retries
```

Пример: 1 000 одновременно ожидающих матча, отдельный запрос каждые 5 минут — 200 запросов в минуту только на результаты. Это условный сценарий нагрузки, а не оценка количества матчей в мире. Если источник позволяет получить пакет из B матчей, запросов на цикл примерно `ceil(M/B)`; учитывать реальные ограничения endpoint и пагинацию.

Измерить типичный день и пиковый день, оставить 20% доступного лимита на retries и служебные запросы. Если лимит ниже необходимого, увеличивать интервал, объединять загрузки и подключать другой проверенный бесплатный источник. Покупка тарифа исключена. Сокращение фактического охвата должно явно отражаться в coverage-report; код не может компенсировать недоступную квоту.

## Что улучшать после первой стабильной версии

| Улучшение | Польза | Когда внедрять | Проверка эффекта |
|---|---|---|---|
| Адаптивный опрос по статусу и близости конца | Меньше запросов при той же свежести | Измерен расход квоты | Запросы на матч снижаются, p95 задержки сохраняется |
| Второй источник | Расширение охвата и устойчивость | Выявлены реальные пропуски | Меньше missing results без роста ошибочных объединений |
| Dashboard покрытия и очереди | Быстрее замечать пропуски | CLI неудобен оператору | Время обнаружения/устранения сбоев уменьшается |
| Conditional requests / кэш источника | Меньше трафика | Провайдер поддерживает ETag/Last-Modified | Снижение байтов и времени, без потери обновлений |
| Несколько worker | Быстрее обработка очереди | Очередь растёт при свободной квоте | Меньше overdue jobs, общий лимит соблюдается |
| Отдельная очередь сообщений | Более сложная маршрутизация | Задания БД стали измеренным ограничением | Улучшение throughput оправдывает поддержку новой системы |
| Подробная лента событий матча | Расширение обязательного live-отображения | Есть потребность и доступный бесплатный источник | Корректный порядок событий без нарушения лимитов |
| Go/Rust для отдельных частей | Меньше CPU/памяти | Профилирование показывает CPU bottleneck | Сравнение на одинаковой нагрузке и результатах |
| Исторический архив | Долгосрочная аналитика | Пользователь изменил правило 72 часов | Новая политика хранения явно утверждена |

## Меры, перенесённые в обязательное ТЗ 1.1.0

| Риск | Принятое решение | Остаток риска | Статус |
|---|---|---|---|
| Платный доступ | Два источника без ключа, без платных зависимостей | Источник может прекратить бесплатный доступ | Реальный запуск проверен |
| Квота/блокировка | Пакетные страницы, лимиты в БД, cooldown/circuit, адаптивный опрос | Свежесть снижается при ограничениях | Базовые сценарии проверены; пилот предстоит |
| Повреждённые данные | Контрактные тесты, валидация, карантин и блок-детектор | Источник может вернуть правдоподобный неверный результат | Основные ошибки проверены; детектор 80% ещё нужен |
| Отказ источника | Маршрутизация на проверенный бесплатный резерв | Для части лиг резерва может не быть | Закреплено в ТЗ, не реализовано |
| Неполный охват | Паспорт, каталог и состояния успешного сбора | Полнота не подтверждается успешной выборкой | Частично; gap/reconciliation ещё нужны |
| Нет точного времени конца | Anchor=observed и явная подпись | Точные 72 часа от фактического конца неизвестны | Реализовано и проверено |
| Возврат старых матчей | Retention, маркеры, ограничение истории | Нужен пилот длительного хранения | Основные сценарии проверены |
| Дубли и конфликты | Пространства ID разделены, fuzzy-объединения нет | Один матч может присутствовать у двух источников | Безопасная изоляция есть; aliases/fallback не реализованы |
| Сон/выключение ПК | Постоянные задания, lease, heartbeat | Во время выключения сбора нет | Рестарт лимитов/lease проверен; длительный простой ещё проверить |

Эти меры уменьшают риски после реализации и проверки. Риск считается закрытым только по результатам тестов и пилота; изменения документов сами по себе не устраняют его. Точное поведение описано в разделе 12 ТЗ.

## План измерений пилота

Дополнительные обязательные меры для web UI/live (ТЗ 1.3.0):

| Риск | Решение | Оставшееся ограничение |
|---|---|---|
| Бесплатный источник не передаёт тайм/минуту | Nullable-поля и flags покрытия, подпись «Недоступно», запрет вычисления от kickoff | Минуты доступны только для части лиг |
| Задержанный счёт выглядит текущим | Время наблюдения и явная отметка свежести/задержки | Источник может обновляться редко |
| Интерфейс зависает на сети | Асинхронный fetch, отмена старых запросов, async Python I/O; сбор вынесен в worker | Требуется браузерная проверка и замер |
| Ответ старой лиги приходит после смены выбора | ID и номер UI-запроса, отбрасывание устаревшего ответа | Нужны тесты быстрых переключений |
| Частые клики исчерпывают квоту | GUI читает локальный API; внешний сбор только через worker | Свежесть ограничена внешним расписанием |
| Матч остаётся на экране после 72 часов | Локальная проверка expires_at, очистка карточки/кэша, проверка после сна | Физическое удаление БД зависит от доступности worker |
| LIVE резко увеличивает трафик | Общая страница активных матчей, план квот, эффективные интервалы | Бесплатный режим не гарантирует realtime |
| Тяжёлый frontend | Шаблоны, локальный небольшой JS/CSS, предел 200 KB без внешних ресурсов | Реальный размер нужно проверить |
| Названия команд замедляют список | API возвращает home/away ID и name одним ответом; join/пакетная выборка без N+1 | Проверить SQL и p95 на нагрузочном профиле |
| Неверные/небезопасные имена команд | Unicode, экранирование HTML, порядок хозяева/гости, диагностика отсутствующего имени | Источник может ошибиться в названии |
| Сохранение настроек через веб | Origin/CSRF, серверная валидация, локальный bind; auth при сетевом доступе | Требуется проверка write-endpoint |

Web UI и основное live-отображение реализованы. Браузерные проверки подтвердили цепочку списков, сохранение настроек, отсутствие XSS, мобильную компоновку и скорость; API/retention проверены автоматически. Реальная минута есть у части HTML-карточек, тайм чаще отсутствует. Статусы «нужно проверить» выше являются требованиями расширенного пилота, а не отсутствием всей реализации.

|---|---|---|---|
| R-014 | SQLite отличается от исходного PostgreSQL-профиля | WAL, короткие транзакции, индексы, один collector по lease; нагрузка 100k/20 клиентов измерена | Ограниченный ресурсами профиль; миграции схемы и решение о PostgreSQL перед масштабированием / P1 |
| R-015 | HTML-контракт Sky не документирован как API | Изолированный адаптер, проверка карточек/даты, карантин, консервативная частота | Пилот и наблюдение изменений; источник может отключиться / P0 |
| R-016 | В текстовой дате Sky нет года/UTC-зоны | Дата URL + сверка дня/месяца, Europe/London с DST, паспорт | Перекрёстная проверка дат и часового пояса; stale-content того же дня другого года возможен / P1 |
| R-017 | Названия лиг не дают достоверную страну | Известные коды/эвристика, отдельная «Страна не указана» | Проверенный реестр классификации и ручные overrides / P1 |
| R-018 | У двух источников разные ID одного матча | Не объединять автоматически; источник явно виден | ID/aliases и безопасная маршрутизация резервов / P1 |
| R-019 | API OpenLigaDB не подтверждает текущий live | Unknown вместо выдуманного LIVE, минута null | Источник с явным live; не вычислять таймер / Принятое ограничение |
| R-020 | После auto-refresh дальнейшая UI-страница теряется | Ограничение описано в руководстве; повторная загрузка доступна | Сохранить загруженные страницы и выбранный матч при обновлении / P2 |
| R-021 | Зависшие неопределённые матчи не истекают | Не удалять без подтверждения; статус виден | Alert >24 часов и сверка исчезнувших матчей / P1 |
| R-022 | Worker обходит источники последовательно | Сеть асинхронная, UI независим, lease предотвращает дубли | Один медленный источник может задержать другой на время timeout; разнести задачи при необходимости / P1 |
| R-023 | QA-скриншоты содержат реальные команды/результаты | Исключены из Git; удаление PNG через 72 часа в cleanup | Пользовательские копии вне программы не контролируются / P1 |
| R-024 | Тесты не подтверждают недельную стабильность | 32 автоматических + реальный браузер/HTTP и нагрузочный замер | Семидневный игровой пилот; не объявлять 1.0 / P0 |
| R-025 | Новая Starlette предупреждает об устаревающем TestClient/httpx | Версии зафиксированы; тесты проходят | Обновить тестовый транспорт перед следующей сменой зависимостей / P2 |
| R-026 | Старые долгоживущие матчевые payload могут остаться в свободных страницах SQLite | Рабочие строки удаляются; API недоступен | Если требуется физическое стирание носителя, добавить secure_delete/политику бэкапов; текущие 72 часа — логическое хранение / P1 |

Фактические замеры и воспроизведение: [VERIFICATION_REPORT.md](VERIFICATION_REPORT.md). Новые риски добавлены без объявлений об их полном устранении.

Во время пилота записывать агрегаты: число соревнований с подтверждённым покрытием, успешные запросы, расход квоты, p50/p95 задержек, размер очереди, долю неизвестных статусов и результатов, длительность очистки, CPU/RAM и объём БД. Не включать содержимое матчей в долгоживущие диагностические записи.

Разделять задержку публикации у провайдера и задержку собственного опроса. Проверять доступность результата по независимым timestamps, если они есть; иначе обозначать метрику как оценочную. Выбирать оптимизации по измерениям, а не по впечатлению, что Python недостаточно быстр.
