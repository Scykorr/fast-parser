# Эксплуатация, диагностика и восстановление

Описание кода 0.13.1, 11.10.2026. Пользовательский интерфейс —
[USER_GUIDE.md](USER_GUIDE.md), разработка — [DEVELOPER_GUIDE.md](DEVELOPER_GUIDE.md).
Не воспринимать все описанные сценарии как пройденный недельный пилот.

## 1. Штатный запуск и остановка

```powershell
.\start.cmd
# Или с выбором порта:
.\start.ps1 -Port 8001
```

Первое заполнение включает справочники/страницы и 30-секундные квоты. Пустая таблица
в первые секунды ожидаема. РПЛ пустая из-за неподключенного адаптера, не ожидания квоты.
Новая чистая БД не содержит старые 137 legacy записей сама по себе.

```powershell
.\stop.cmd
# Если запуск на 8001:
.\stop.cmd --port 8001
```

Stop работает только для managed serve. Прямой uvicorn или старый экземпляр без
control-файла остановить Ctrl+C в его терминале. Неудача stop не является основанием
убить любой python.exe. Если нет control-файла, сообщение «нет managed-server» не
доказывает, что порт вообще свободен.

Не удалять server/stop JSON во время запуска: token связывает конкретный экземпляр.
При занятом порту установить владельца порта и использовать иной порт/штатную остановку.
Изменение control JSON не способ восстановления состояния источников.

## 2. Быстрый диагноз

```powershell
Invoke-RestMethod http://127.0.0.1:8000/health/live
Invoke-RestMethod http://127.0.0.1:8000/health/ready
# ok только при свежем worker и неустаревших карточках; иначе HTTP 503 и status=stale.
# В теле есть collector_fresh и data_age_seconds. /health/live проверяет сам процесс.
Invoke-RestMethod http://127.0.0.1:8000/api/v1/diagnostics
Invoke-RestMethod http://127.0.0.1:8000/api/v1/settings
```

Проверять последовательно:

1. Процесс отвечает? health/live.
2. База/настройки читаются? health/ready.
3. worker_heartbeat меняется? Не равен ли FAST_PARSER_WORKER 0, есть ли чужой lease?
4. Активное окно сбора сейчас открыто в timezone Settings?
5. Какой source_policy? Почему collection_allowed/source supported false?
6. source_state closed/open/blocked, error, next_allowed, last_success?
7. league collection_state/last_success_at и next_poll?
8. Матч действительно входит в окно и сезон, не истек ли expires_at?
9. У конкретного матча last_checked_at/is_stale/source_state, не общий успех source?

ready=ok не гарантирует доступность интернета/источников и не означает, что worker
активен. `/metrics` пока содержит только количество лиг/успешных выборок. Для
диагностики пикового дня нужны дополнительные метрики, это открытая задача.

## 3. Частые ситуации

| Симптом | Вероятная причина | Правильное действие |
|---|---|---|
| Первый экран без матчей | План/справочник/квоты | Подождать циклы, посмотреть source/окно, не нажимать sync каждую секунду |
| Одна лига без результата | Дата/сезон вне окна, неизвестный час, отказ source | Проверить фильтры и причину; сохранить контекст |
| РПЛ «Сбор недоступен» | Нет подтвержденного официального адаптера | См. handoff; reset не включает отсутствующий код |
| legacy sync 422 | official_only=true | Ожидаемая защита, не ошибка нового parser |
| CAPTCHA/403 | Источник blocked | Остановить retry, расследовать официальную доступность |
| 429 | Rate limit | Ждать Retry-After/next_allowed; не reset |
| ConnectTimeout | Сеть/TLS/сервер | Backoff, повтор после срока; не считать неверными команды/счет |
| Карантин SchemaError | Контракт изменился | Исправить parser/тесты до повторного сбора |
| CLI «worker уже работает» | Lease активного сервера | UI sync или stop managed serve |
| UI «данные задержаны» | Старое наблюдение/открытый circuit | Показать последнее наблюдение, не имитировать live |
| settings «неизвестная лига» | В списке shortcut, которого нет ни в каталоге, ни среди bl1/bl2/bl3/pl/la1/ucl/dfb | Убрать чужой ID. Исторический список на чистой установке сохраняется и не требует платного fallback |
| browser smoke не находит Sky | Старая предпосылка теста | Новая official-first/isolated проверка |
| Старый changes cursor получает 410 | Журнал очищен | Полная синхронизация потребителя |
| После restore events пропали | Восстановлена старая seq-история | Полная синхронизация, прежний cursor не использовать |

## 4. Ошибка схемы и повторное включение

Сначала записать source, текущую версию, дату/league ID, raw_status/структурные признаки,
HTTP status и исключение без challenge-token. Не сохранять произвольный реальный архив.
Сделать минимальный synthetic fixture и regression-тест. Проверить, что предыдущая
принятая партия сохранена и новые финалы не теряют TTL.

Обычный open/quarantine ожидается через next_allowed; POST reset предназначен только
для blocked. Для исправленного blocked-источника оператор может явно запросить
повторную проверку через UI. Не снимать 403/429/CAPTCHA SQL-обновлением, не менять
last_success или failures для красивой диагностики. РПЛ reset возвращает 422,
поскольку ее адаптер не реализован.

Ручной sync сбрасывает задачу/план, а не квоту. Если источник не due/cooldown, 202
означает принятие заявки и может не дать HTTP к провайдеру немедленно. Для shared-source
сброс может касаться обеих лиг. Следить за последующим last_checked_at, а не 202.

## 5. Логи и данные

Логи CLI выводятся в терминал через logging. Отдельного обязательного log-файла нет.
Source error ограничен длиной и хранится в source_state. Не логировать секреты,
stop-token, Authorization, challenge query или полный HTML ответ.

Не коммитить `data/`, SQLite/WAL/SHM, `.venv/`, snapshots/QA, runtime JSON. Для передачи
описания проекта достаточно исходников, lock, docs и тестов. Для переноса рабочего
состояния нужна отдельно согласованная копия SQLite с учетом TTL и конфигурации.

## 6. Резервная копия

Предпочтителен штатный sqlite3 backup, а не копирование одного .sqlite3 во время WAL-записи.
Пример после штатной остановки, путь назначения новый и внутри data:

```powershell
.\stop.cmd
New-Item -ItemType Directory -Force -Path data\backups | Out-Null
.\.venv\Scripts\python.exe -c 'import sqlite3; from pathlib import Path; from datetime import datetime, UTC; src=sqlite3.connect("file:data/football.sqlite3?mode=ro", uri=True); target=Path("data/backups")/("football-"+datetime.now(UTC).strftime("%Y%m%dT%H%M%SZ")+".sqlite3"); dst=sqlite3.connect(target); src.backup(dst); dst.close(); src.close(); print(target)'
```

Это пример процедуры, не действие, автоматически выполненное при подготовке docs.
При FAST_PARSER_DB измененном пути адаптировать source, не создать по ошибке новую
пустую БД. Для backup проверить существование источника, свободное место, права.
Не считать незнакомый backup корректным без PRAGMA integrity_check/user_version.

Собственные copies в data/backups автоматически cleanup не удаляет. Оператор должен
объявить/обеспечить их срок, в текущем продукте бессрочный архив матчей не требовался.
Автоматические migration .v1.bak/.v2.bak/.v3.bak очищаются по возрасту 72h; сторонние копии — нет.
Текущая схема — user_version 4. Архив финалов живёт в таблице results и не равен списку на экране.

## 7. Проверка восстановления на изолированной копии

1. Сначала остановить записывающий процесс и сделать текущую backup-копию.
2. Не заменять рабочую БД до проверки; выбрать новый путь, например data/restore-check.
3. Проверить integrity_check и user_version копии read-only.
4. Запустить копию без worker на отдельном порту:

```powershell
$env:FAST_PARSER_DB = (Resolve-Path data\restore-check\football.sqlite3).Path
$env:FAST_PARSER_WORKER = '0'
.\.venv\Scripts\python.exe -m fast_parser serve --port 8001
```

5. Проверить health/ready, Settings, каталог/пометки, неистекшие карточки и ошибки API.
6. Истекшие на текущую дату карточки должны скрыться, а не считаться потерянными.
7. Остановить именно port 8001; восстановить прежние env в терминале.
8. Для рабочей замены только после проверки выбрать конкретную копию, остановить
   процесс, сохранить текущую базу и ее служебные файлы. Не смешивать WAL/SHM старой
   базы с новым snapshot; не использовать wildcard-удаление всей data.
9. Клиентам changes выполнить full resync, сохранив новую watermark; старый cursor
   восстановленной базы не дает безопасной позиции.
10. После разрешенного запуска worker подтвердить квоты/plan recovery и истечение TTL.

Процедура восстановления должна быть отдельно испытана; наличие инструкции не
закрывает соответствующий пункт roadmap. Не изменять timestamps копии для «обновления»
срока матчей. Не отключать защиту базы новой версии ради старого кода.

## 8. Перенос компьютера/редактора

Клонировать репозиторий, выбрать поддерживаемый Python, пересоздать .venv по lock,
прочитать Cursor handoff, выполнить изолированные tests. Git не переносит текущие
матчи/настройки, это ожидаемо. Если нужна копия состояния — использовать процедуру выше.
Персональный путь Node/Playwright и absolute .venv со старого ПК не подходят на новом.

Не требуется запускать npm для UI, оплачивать API или логиниться на источниках.
Если новый источник требует оплату/ключ с платной зависимостью, он не соответствует ТЗ.

## 9. Длительный пилот

Перед 7 сутками: согласовать объявленный охват, проверить чистую установку/настройки,
резервную копию/restore, bounded attempts и задачи отсутствующих результатов.
Собирать агрегаты по source: успешность/ошибки, lag конкретных матчей, долю unresolved,
задержку очереди, число запросов/429/403, TTL удаления, SQLite busy и browser errors.

На каждом инциденте различать неполноту провайдера и задержку собственного обхода.
Не называть stale карточку достоверной только потому, что source в целом closed.
Работать по согласованному окну, не опрашивать все мировые лиги каждую секунду.
По завершении приложить датированный отчет с пределами измерений; 131 unit-тест
не заменяет 7 суток и не закрывает live-статусы непротестированных источников.
