## Как читать старые документы без ошибочных выводов

В ТЗ/roadmap/руководстве есть разделы первоначальной 0.7.0 и последующие дополнения.
Не переносить старое описание OpenLigaDB/Sky на текущую политику official_only.
Документы передачи описывают текущую реализацию; исторические разделы сохраняют контекст.
Требование пользователя важнее старого проектного решения. При расхождении описания
с кодом отметить его, проверить тестом и обновить соответствующий документ.
Сначала искать актуальное дополнение/дату проверки, затем историческую часть.

Счетчик 147 — результат конкретной локальной базы 06.10.2026, не гарантированный
размер каталога новой установки. В чистой базе startup создает 10 официальных записей,
из них 9 имеют рабочий сбор, одна — неподключенная РПЛ. Проверка источников от
06.10.2026 не подтверждает их доступность 11.10.2026 без нового запроса.

## Карта обновления документов

| Изменение | Что обновить |
|---|---|
| Только документация | Индекс, handoff и затронутые руководства; запись даты/проверки |
| Новый источник | Паспорт страны, SOURCE_DEVELOPMENT, SOURCES/OFFICIAL_SOURCES, ТЗ, roadmap, риски, changelog, отчет |
| Хранение/миграция | ARCHITECTURE, API_INTEGRATION, OPERATIONS_RUNBOOK, ТЗ, тесты восстановления, отчет |
| API | API_INTEGRATION, ARCHITECTURE, клиентские примеры и критерии совместимости |
| UI | USER_GUIDE, browser-проверки/отчет, доступность/мобильная ширина |
| Релиз | `__init__.py` и `pyproject.toml` синхронно, CHANGELOG, ROADMAP, отчет; новый tag отдельно |

Не копировать полные схемы/списки открытых задач во все файлы: давать ссылку на
основной документ. В отчетах отделять автоматический тест, реальный сетевой прогон
и длительный пилот. Наличие текста не заменяет выполненную проверку.
