official_only включен по умолчанию, без автоматической подмены сторонними данными.

## 1. Цель и анализ задачи

Создать работающий сервис, который по настраиваемому расписанию получает список футбольных матчей в заданном диапазоне дат, затем обновляет их статусы и результаты. Завершённые матчи доступны 72 часа после окончания, затем удаляются из рабочего хранилища.

Python подходит для первой версии: при сетевом сборе основное время обычно занимает ожидание ответа. Асинхронные запросы, пакетные выборки и индексы БД важнее раннего переписывания на Go или Rust. Решение о другом языке принимать по измерениям CPU, памяти и пропускной способности.

«Все мировые лиги» — целевой охват, который нельзя подтвердить без согласованного перечня соревнований и проверки источников. Продукт должен показывать фактическое покрытие, пропуски и ограничения, а не заявлять абсолютную полноту. Кубки, сборные, женские, молодёжные и любительские соревнования — отдельные категории, включаемые настройками.

Обязательное ограничение: получение данных бесплатно. Платные API, пробные периоды с последующей оплатой, платные прокси, сервисы решения CAPTCHA и облачные браузеры не допускаются как обязательные зависимости. Сервис запускается на имеющемся компьютере без обязательной платной инфраструктуры; интернет, электричество и оборудование не обещаются бесплатными. Во время работы сервис не вызывает нейросети и не расходует токены.

Источники: бесплатные документированные API и открытые страницы расписаний/результатов через независимые HTML-адаптеры. Бесплатный API допустим, но не должен превращаться в платную зависимость. При закрытии бесплатного доступа источник отключается, данные помечаются устаревшими, используется другой проверенный бесплатный источник. Автоматическая покупка доступа запрещена.

## 2. Границы первой версии

Входит: лёгкий веб-интерфейс в браузере, Python-бэкенд, связанные списки стран/лиг/матчей с названиями обеих команд, реестр лиг и сезонов, расписание, текущий и итоговый счёт, статусы, тайм и минута при наличии в источнике, настройки времени, хранение, очистка, CLI, HTTP API чтения и диагностики, Docker для backend, журналирование и автоматические проверки.

Не входит в обязательную первую версию: прогнозы, коэффициенты, видеотрансляции, статистика игроков и подробная лента событий. GUI и поддержка отображения live-счёта обязательны для 1.0; наличие минуты/тайма в конкретной лиге зависит от бесплатного источника и отражается в покрытии.

Нужно уточнить перед подключением реального источника:

- Дополнительные желаемые сайты и допустимый способ использования/публикации данных. Бюджет уже установлен: 0 рублей; заново спрашивать о покупке API не нужно.
- Перечень категорий футбола и эталонный перечень лиг для проверки покрытия.
- Требуемую задержку получения результата, число пользователей и место запуска.
- Требуется ли доступ к истории старше 72 часов. Веб-интерфейс уже обязателен; по умолчанию сервер запускается локально, страница открывается в браузере.

До уточнения использовать значения по умолчанию из этого ТЗ. Реальную интеграцию не объявлять завершённой без проверенного доступа к выбранному источнику.

## 3. Настройки и значение «по времени»

Разделить три независимые настройки:

1. Диапазон матчей: абсолютные `date_from`/`date_to` либо скользящее окно `lookback_days`/`lookahead_days`.
2. Частоту запросов: отдельные интервалы для расписаний, ожидаемых результатов и перепроверки итогов.
3. Окна работы: необязательные часы запуска по часовому поясу пользователя; по умолчанию сервис работает круглосуточно.

Все timestamps в БД и заданиях — UTC, timezone-aware. Пользовательский часовой пояс по умолчанию `Europe/Moscow`; поддерживать IANA-зоны. Интервал дат трактовать как `[from, to)`, календарную конечную дату в интерфейсе явно объяснять. Проверять `from < to`. Режимы абсолютного и скользящего окна взаимоисключающие.

Предлагаемый конфиг, подлежащий валидации и описанию в README:

```yaml
timezone: Europe/Moscow
cost_policy:
  paid_services_allowed: false
  monthly_data_budget: 0
selection:
  mode: rolling
  lookback_days: 3
  lookahead_days: 7
  competitions: all_supported
schedule:
  fixtures_interval_seconds: 21600
  results_interval_seconds: 300
  live_interval_seconds: 120
  final_recheck_interval_seconds: 21600
  cleanup_interval_seconds: 300
  active_windows: []
retention:
  finished_seconds: 259200
  cancelled_seconds: 259200
  unresolved_alert_after_hours: 24
http:
  timeout_seconds: 20
  max_attempts: 4
  global_concurrency: 8
  per_host_concurrency: 1
sources:
  - name: primary
    adapter: openligadb
    enabled: true
    priority: 1
    access_mode: free_no_key
    requests_per_minute: 6
    min_request_spacing_seconds: 10
    quota_reserve_percent: 20
```

`openligadb` — первый адаптер, который необходимо реализовать и проверить. Шесть запросов в минуту и пауза 10 секунд — собственный консервативный стартовый предел, а не объявленная квота OpenLigaDB; более строгие опубликованные ограничения имеют приоритет. Для HTML-источников начать не чаще одного запроса в 15 секунд на домен, с concurrency=1. Для каждого источника явно задавать режим доступа и пределы. Ключи необязательных бесплатных API и URL БД передавать через переменные окружения. Добавить `.env.example` без секретов. Изменения конфигурации применять после безопасного перезапуска; hot reload не обязателен.

## 4. Сбор и жизненный цикл

- При старте загрузить конфигурацию, проверить БД и миграции, восстановить просроченные задания, обновить реестр доступных соревнований.
- Получать расписание пакетами по датам/лигам согласно возможностям источника; обрабатывать пагинацию до конца.
- Сохранять матчи транзакционным upsert. Повторный сбор не создаёт дубликаты.
- Для каждого матча рассчитывать `next_poll_at`; фактический лимит источника имеет приоритет над желаемой частотой.
- Начиная с предполагаемого окончания, проверять результат каждые 5 минут. Предполагаемое окончание — только время начала плюс настраиваемые 120 минут для планирования запросов, оно не подтверждает завершение.
- При наличии пакетного запроса результатов использовать его вместо отдельного запроса на каждый матч. Вне рабочего окна опрос приостанавливать, после открытия выполнять объединённый догоняющий сбор без лавины запросов.
- После подтверждённого завершения сохранять результат и перепроверять его каждые 6 часов до истечения хранения.
- Ошибка источника или отсутствие матча в ответе не означает отмену, окончание или удаление.

Нормализованные статусы: `scheduled`, `live`, `paused`, `finished`, `postponed`, `cancelled`, `abandoned`, `unknown`. Хранить исходный статус отдельно. Неизвестное значение переводить в `unknown` и фиксировать предупреждение. При переносе обновлять начало и задания без дублирования матча. Для прерванных игр ждать решения источника. Разрешать исправления финального результата с записью причины и источника.

Счёт хранить отдельно за основное время, дополнительное время и серию пенальти. Неизвестный счёт — `null`, а не 0:0. Счёт серии пенальти не складывать со счётом игры. Техническую победу помечать отдельно, не придумывать счёт. Победитель может отсутствовать при ничьей.

## 5. Хранение и правило 72 часов

Для завершённых матчей:

```text
retention_anchor_at = достоверное finished_at от источника
                     иначе first_observed_finished_at
expires_at = retention_anchor_at + 72 часа
```

Хранить метод определения времени окончания: `source` или `observed`. При отсутствии точного времени допускается более длительное хранение от первого обнаружения завершения; это явная погрешность, а не выдуманное время окончания. Если источник позднее сообщает достоверное время, пересчитать срок; если он уже прошёл, не публиковать запись.

API исключает истёкшие матчи сразу по условию `expires_at <= now`, физическая очистка проходит каждые 5 минут. Исправление счёта не продлевает срок. Исправление ошибочного статуса обратно в незавершённый снимает срок и пересоздаёт задания, пока запись ещё существует.

Поздно обнаруженный матч с достоверным окончанием более 72 часов назад не сохранять в доступной коллекции. Временные staging-данные удалить после обработки. Перенесённые, неизвестные и прерванные матчи не удалять автоматически по правилу завершения: через 24 часа неопределённости создавать диагностический сигнал и продолжать редкий опрос. Отменённые матчи удалять через 72 часа после первого подтверждения отмены — отдельная политика.

При удалении каскадно удалять результаты, связанные задания, подробную историю, исходные payload и кэши. Приложение не должно повторно добавлять истёкший матч при повторном сборе: использовать окончание из источника либо минимальный маркер удаления `(source, external_match_id, deleted_at)` без команд и результатов. Срок маркеров — минимум горизонт повторного сбора плюс 72 часа. Маркер не блокирует явно подтверждённое возобновление или новое начало матча; такая смена проверяется адаптером.

Резервные копии и внешние выгрузки имеют собственный срок хранения. Если 72 часа означает удаление вообще всех копий, запретить выгрузки и бэкапы с более длительным сроком; согласовать это до эксплуатации. По умолчанию 72 часа относится к рабочему хранилищу и API.

## 6. Модель данных

PostgreSQL — основная БД. Минимальные сущности:

| Сущность | Обязательные поля |
|---|---|
| Source | id, name, adapter, priority, enabled, last_success_at |
| Competition | id, country, name, category, enabled |
| Coverage | source_id, external_competition_id, competition_id, season, fixtures_supported, results_supported, last_verified_at |
| Team | id, name, country (nullable) |
| Match | id, competition_id, season, home_team_id, away_team_id, kickoff_at (nullable), status, raw_status, finished_at, first_observed_finished_at, retention_anchor_method, expires_at, first_seen_at, last_seen_at, updated_at, next_poll_at |
| SourceMatch | source_id, external_match_id, match_id, source_updated_at (nullable), fetched_at |
| Result | match_id, regular_home/away, extra_home/away, penalties_home/away, winner (nullable), is_awarded, source_id |
| Job | id, kind, target_id, due_at, attempts, lease_until, state |
| DeletionMarker | source_id, external_match_id, deleted_at, marker_expires_at |

Технические timestamps по умолчанию nullable только там, где факт неизвестен. Поля счёта nullable, целые неотрицательные. Уникальность `(source_id, external_match_id)`, индексы по `kickoff_at`, `(status, next_poll_at)`, `expires_at`, `(state, due_at)`. Внешние ключи и миграции обязательны.

При нескольких источниках сопоставлять по идентификаторам и таблицам соответствий. Совпадение названий и времени само по себе недостаточно: учитывать соревнование, сезон, команды и переносы. Неуверенные совпадения оставлять раздельными с диагностикой. При конфликте использовать приоритет источников и свежесть его данных; поздно полученный старый ответ не должен перезаписывать более новую информацию. Если источник не отдаёт версию, сериализовать обновления одного матча и сохранять provenance.

## 7. Архитектура и интерфейсы

Рекомендуемый стек: поддерживаемая версия Python 3.12+, `asyncio`, `httpx`, Pydantic, SQLAlchemy, Alembic, PostgreSQL, FastAPI, pytest. Зависимости фиксировать lock-файлом. HTML разбирать библиотекой lxml или selectolax; браузерную автоматизацию подключать только если без выполнения JavaScript источник недоступен.

Модули: `config`, `domain`, `adapters`, `scheduler`, `storage`, `services`, `api`, `cli`, `observability`. Адаптер реализует `list_competitions`, `fetch_fixtures`, `fetch_results`, нормализацию и описание возможностей/лимитов. Доменная логика не зависит от CSS-селекторов или формата конкретного API.

Начать с одного процесса worker и устойчивых заданий в БД. Задания захватывать с lease; после падения lease истекает и работа повторяется безопасно. Не обещать exactly-once: обеспечить at-least-once и идемпотентные изменения. При нескольких worker использовать блокировки БД, исключающие одновременную обработку одного задания. Redis и отдельная очередь не обязательны до появления измеренной потребности.

CLI: `validate-config`, `sync-fixtures`, `sync-results`, `run-worker`, `cleanup --dry-run`, `cleanup`, `coverage-report`. Все команды имеют help, корректные exit codes и общий конфиг. Разовые синхронизации соблюдают лимиты и retention.

API v1:

- `GET /api/v1/competitions` — реестр и покрытие.
- `GET /api/v1/matches` — фильтры дат, соревнований, статуса; cursor pagination, лимит максимум 200.
- `GET /api/v1/matches/{id}` — карточка; удалённый или истёкший матч возвращает 404.
- `GET /health/live`, `GET /health/ready` — процесс и готовность БД.
- `GET /metrics` — для закрытого эксплуатационного доступа.

Ответ содержит UTC-время, источник, свежесть, способ определения окончания и nullable-значения. API не выполняет сбор при каждом чтении. По умолчанию доступ локальный; для внешнего доступа настроить аутентификацию, HTTPS и ограничение запросов. Метрики и административные действия не публиковать открыто.

## 8. Надёжность и диагностика

Таймауты, ограничение размера ответа, проверка HTTP-кодов и схемы обязательны. Для сетевых ошибок, 429 и временных 5xx — до четырёх попыток с exponential backoff и jitter. Уважать `Retry-After`; если ожидание долгое, перепланировать задание. Ошибки 401/403 и невалидный формат не повторять бесконечно. При системных сбоях включать circuit breaker и сигнал оператору. Секреты не выводить в логи.

Лимитер общий для источника и всех worker, учитывает минутный и суточный бюджет, если они есть. При исчерпании бюджета откладывать задачи и показывать устаревание данных. Приоритет: результаты ожидаемых завершений, затем ближайшее расписание, затем перепроверка и дальний горизонт. Предотвращать вечное голодание низкого приоритета.

Структурированные логи: run_id, job_id, source, duration, outcome. Метрики: успешность/длительность запросов, 429, retries, размер очереди, возраст просроченных заданий, задержка результатов, доля матчей без итога, полнота покрытия, число удалений. Ограничивать хранение логов, не писать полные payload по умолчанию. Исходные ответы для отладки хранить только ограниченно и удалять по политике матча.

## 9. Приёмка и проверки

Обязательные автоматические сценарии:

1. Двойной сбор одинаковых данных не создаёт второй матч; перенос обновляет существующий.
2. Цепочка scheduled → live → finished сохраняет итог; null не становится 0; дополнительное время и пенальти разделены.
3. За мгновение до 72 часов матч виден; ровно на границе скрыт; физически удалён в пределах следующего цикла очистки. Использовать управляемые часы без реального ожидания.
4. Время окончания отсутствует, приходит позднее, исправляется; коррекция счёта не обновляет якорь хранения.
5. Старый матч не появляется снова после повторного запроса и после перезапуска; перенос и отмена следуют своим правилам.
6. 429 с Retry-After, timeout, 5xx, 401, повреждённый HTML/JSON: данные не теряются, запросы не зацикливаются, ошибка видна.
7. Падение worker между загрузкой и commit: задание возобновляется, запись не дублируется; два worker не обрабатывают одно задание одновременно.
8. UTC, переход суток и DST в выбранной зоне дают правильное окно запросов.
9. Пагинация источника и API не пропускает и не повторяет матчи; истёкшие строки не попадают в ответ.
10. Контрактные тесты адаптера на сохранённых обезличенных ответах; интеграционные тесты на настоящей PostgreSQL с миграциями.

Предлагаемый профиль нагрузочной проверки, а не обещанная мощность: 100 000 неистёкших матчей, 1 000 ожидающих результатов, 20 параллельных клиентов чтения, контейнеры на 2 vCPU / 4 GB RAM. На этом профиле локальный API списка до 100 записей: p95 ≤ 500 мс; очистка просроченных записей завершается за 5 минут без блокировки чтения. Зафиксировать метод, набор данных, версии и результат замера; при невыполнении оптимизировать или явно согласовать другой профиль.

Целевая задержка обнаружения итогов: 95% не позднее `2 × effective_poll_interval` после доступности источнику. Для проверенных лиг при интервале 5 минут цель — 10 минут; для источников с меньшей пропускной способностью интервал повышается и публикуется отдельно. Приоритеты в бесплатном режиме: отсутствие расходов, корректность и соблюдение ограничений источника, затем свежесть и широта охвата. Задержка публикации самим источником измеряется отдельно. В режиме ограниченных окон цель действует только внутри окна. Не выдавать оценку относительно реального окончания за измерение, если оно неизвестно.

## 10. Что должна предоставить нейросеть-разработчик

Рабочий репозиторий с типизированным кодом, миграциями, lock-файлом, Dockerfile и compose для app/worker/PostgreSQL; примером конфигурации; `.env.example`; README с запуском, настройками, выбранным источником, лимитами и эксплуатацией; тестами и отчётом проверки; OpenAPI; таблицей подтверждённого покрытия.

Порядок работы: проверить OpenLigaDB без ключа → реализовать один сквозной сценарий → проверить retention и восстановления → добавить бесплатный HTML-источник → расширять покрытие. Выбор дополнительных открытых источников входит в работу разработчика и не требует повторного запроса о бюджете. Не заменять настоящую интеграцию фиктивными результатами. Тестовый адаптер допустим только как явно помеченный инструмент тестирования. Не создавать вымышленные endpoint, селекторы или идентификаторы лиг. При недоступном источнике сообщать конкретную причину и сохранять возможность проверки остальных модулей.

Готовность версии определяется критериями приёмки, а не наличием файлов. Не хранить ключи в Git. Не обходить CAPTCHA, авторизацию или блокировки: отключать проблемный адаптер и сообщать о недоступности. Применимость условий конкретного источника проверять при его выборе.

## 11. Проверенные сведения об источниках

На 06.10.2026 документация football-data.org описывает ограничения запросов по тарифам и допустимые null-значения: [API policies](https://docs.football-data.org/general/v4/policies.html). Поэтому лимиты нельзя зашивать едиными для всех провайдеров.

OpenLigaDB — первый бесплатный источник: официальный сайт описывает бесплатный community-проект, получение данных без аутентификации и лицензию ODbL: [описание проекта](https://www.openligadb.de/). Примеры и документация API: [официальный репозиторий](https://github.com/OpenLigaDB/OpenLigaDB-Samples). Community-данные требуют проверки полноты; одноимённые лиги могут быть дублями или плохо поддерживаться. Лицензию учитывать при использовании и распространении объединённой базы, сохранять указание происхождения данных.

football-data.org допустим только как необязательное дополнение на Free Tier: [бесплатное покрытие](https://www.football-data.org/coverage), [условия тарифов](https://www.football-data.org/pricing). Бесплатный план имеет ограниченный охват и задержанные данные; ключ получает пользователь через бесплатную регистрацию. Запуск основной версии не должен зависеть от этого ключа. Платные планы не использовать. Сведения проверены по документации, работоспособность адаптеров ещё не проверена.

## 12. Обязательные меры снижения рисков в бесплатном режиме

### 12.1. Проверка и маршрутизация источников

До включения адаптера оформить паспорт источника: официальный URL, способ доступа, стоимость 0, необходимость регистрации, ссылки на условия/robots.txt, дата проверки, ограничения запросов, supported seasons, пагинация, наличие ID/статуса конца, правила счёта, наблюдаемая свежесть. Robots.txt учитывать вместе с условиями доступа: он сам по себе не доказывает разрешение на любое использование. Страница с платным доступом или регулярной блокировкой не становится обязательным источником.

Разработчик должен самостоятельно обследовать открытые сайты результатов и официальные страницы лиг, выбрать хотя бы один доступный HTML-источник с расписаниями и итогами и подтвердить его реальными ответами. Конкретный сайт здесь не объявляется проверенным. Если подходящего HTML-источника нет, выполнить API-часть и явно оставить критерий HTML незавершённым; не подменять его моками.

Для каждой лиги назначить основной и, если найден, резервный источник. Резерв опрашивать при ошибке основного или просроченном результате, а не постоянно дублировать весь трафик. Оба используют общие идентификаторы соответствий. Если резерв отсутствует, поле `redundancy=none` должно быть видно в coverage-report. Полнота — относительно согласованного реестра; пустой ответ не доказывает отсутствие матчей.

В таблицу Coverage добавить `state` (unverified/verified/degraded/unavailable), `redundancy`, `effective_poll_interval`, `last_success_at`, `last_fixture_sync_at`, `last_result_sync_at`, `gap_reason`. В Source добавить `access_mode`, `cost=0`, `terms_checked_at`, `circuit_state`, `next_allowed_request_at`. У каждого матча показывать `result_verified`, `data_freshness` и время последнего успешного наблюдения. Двойное подтверждение финала полезно, но не обязательно при единственном источнике: хранить `verification=single_source` и не выдавать его за независимую проверку.

### 12.2. Экономия запросов и защита от блокировок

Объединять задачи в один запрос по URL/дате/лиге. После получения общей страницы обновлять все матчи с неё и перепланировать их вместе. Не скачивать одну страницу отдельно для каждого матча. Кэш запроса ограничивать временем до ближайшего следующего опроса; очистка матчей также очищает содержащие их payload.

Если доступны ETag/Last-Modified или endpoint времени изменения, использовать их. 304 не тратит парсинг, но всё равно считается запросом в квоте. Повторно использовать HTTP-соединения, применять явный User-Agent. Не использовать смену прокси или аккаунтов для обхода ограничений.

Лимитер хранит состояние в БД и не сбрасывает бюджет после перезапуска. На 429 учитывать Retry-After; без него пауза минимум 60 секунд с дальнейшим увеличением до часа. После 5 последовательных временных ошибок открывать circuit на 15 минут; затем один пробный запрос. Повторные сбои увеличивают паузу до часа. 403/CAPTCHA останавливают источник до проверки оператором; бессмысленные retries запрещены. Обнаружение странички блокировки под HTTP 200 обязательно.

Рабочий бюджет — 80% заданного лимита, 20% резерв для восстановления. Это не разрешение превысить лимит. Для пакета матчей начинать опрос у предполагаемого конца, затем интервалы 5, 10, 20, 30, 60 минут при отсутствии подтверждённого итога; после 24 часов — каждые 6 часов с предупреждением. Эти интервалы могут только увеличиваться из-за ограничений источника. Обеспечить ежедневную сверку каждой включённой лиги и показать, если она невозможна в доступном бюджете. Перед запуском `plan-collection` вычисляет ожидаемые запросы и эффективные интервалы; невыполнимый план не скрывается.

### 12.3. Защита качества и хранения

Перед публикацией проверять структуру, ID, пары команд, типы счёта, финальный статус и границы дат. Скачанный HTML входа/ошибки не считать расписанием. Резкое падение числа элементов более чем на 80% относительно успешной выборки того же диапазона — сигнал для повторной проверки, а не автоматическое доказательство поломки: сезонные изменения возможны. Невалидную выборку помещать в краткоживущий карантин; предыдущие корректные записи сохранять до срока удаления. Пустой валидный ответ обрабатывать отдельно от ошибки.

Совпадение команд нормализовать через ID и таблицы aliases. Fuzzy-поиск может предлагать совпадение, но не объединять автоматически. При несовместимых финальных счетах выставлять `result_verified=false`, сохранять конфликт до expires_at и выполнять ограниченную перепроверку. Временем обновления счёта не подменять время окончания матча.

Очистку выполнять пачками до 1 000 матчей в транзакции с индексом expires_at. Публикация из БД, API-кэши и перечни матчей одинаково проверяют срок. Маркеры удаления для матчей без точного finished_at продлевать при повторном наблюдении старого завершённого ID; исторические запросы за рамками настроенного lookback запрещать в обычном режиме. При расширении диапазона не восстанавливать истёкшие результаты из старых маркеров.

`plan-collection`, `source-check`, `coverage-report` и диагностика конфликтов доступны через CLI бесплатно, без внешних мониторинговых сервисов. На локальном компьютере документировать работу при отключении сети, уходе в сон и перезапуске: после восстановления — объединённый catch-up, но матчи, уже удалённые по сроку, не возвращаются.

### 12.4. Дополнительная приёмка

- Чистый запуск работает без платного аккаунта и без API-ключа на реальном OpenLigaDB; выбранная лига подтверждена текущими ответами, ID не выдуманы.
- Реальный HTML-адаптер получает расписание и хотя бы один итог бесплатно; сохраняются обезличенные образцы для контрактных тестов.
- 100 матчей с одной страницы вызывают одну загрузку за цикл, а не 100.
- 429, 403, HTTP 200 с CAPTCHA, изменение HTML, пустая страница и сетевой обрыв дают разные диагностические состояния; неверные итоги не публикуются.
- Лимиты и cooldown сохраняются после рестарта; параллельные worker не увеличивают общий разрешённый трафик.
- Отказ основного источника включает только проверенный бесплатный резерв; отсутствие резерва явно отображается.
- Изменение Free Tier на платный доступ отключает источник и не требует оплаты для работы остальных источников.
- Конфликт счетов, некорректный alias, перенос, очистка payload и повторный импорт без finished_at покрыты тестами.
- До версии 1.0 проведён семидневный пилот на бесплатных источниках с отчётом охвата, задержек, ошибок и расхода запросов. Ограничения остаются видимыми в отчёте.

## 13. Остаточные ограничения и история

Кодом можно снизить риск потерь, дублей, перегрузки и неверного удаления. Нельзя гарантировать бесплатно доступ ко всем мировым лигам, точное фактическое время конца при отсутствии этого поля, работу стороннего сайта без перерывов или публикацию им верного результата. Для таких случаев обязательны обнаружение, резерв при наличии и честная диагностика; отсутствие покрытия нельзя исправлять вымышленными данными.

1.2.0 (06.10.2026): GUI включён в обязательную 1.0; добавлены связанные списки, карточка матча, live-счёт, nullable-тайм/минута, правила свежести и проверки интерфейса.

1.3.0 (06.10.2026): настольный GUI заменён лёгким веб-интерфейсом; Python-бэкенд обязателен; уточнены названия команд, размер ресурсов и показатели скорости. Исторические записи выше описывают предыдущие редакции; актуальные требования приведены ниже.

## 14. Графический интерфейс — обязательная часть 1.0

### 14.1. Технология и запуск

Основной вариант — лёгкий веб-интерфейс: Python + FastAPI, HTML-шаблоны Jinja2, локальные CSS и небольшой JavaScript без обязательного SPA-фреймворка и Node.js-сборки. Страница и API обслуживаются одним приложением с одного origin. Сбор, лимиты и запись БД остаются в отдельном worker. По умолчанию сервер слушает только 127.0.0.1; интерфейс открывается по локальному URL в браузере. Поддержать локальный запуск на Windows и Linux. В README предоставить одну команду/скрипт запуска сервисов, URL, проверку готовности и понятное сообщение при недоступной БД. Первичная установка описана отдельно. Docker допустим для backend/БД; браузер работает вне контейнера.

Изменения фильтров и обновления выполнять асинхронным fetch без полной перезагрузки страницы. Использовать AbortController и номер запроса для отмены устаревших ответов. Браузер не содержит селекторы источников, не скачивает внешние сайты напрямую и не расходует их квоты при каждом клике. Закрытие вкладки не останавливает worker; прекращение сбора выполняется явной командой сервера. Python HTTP-обработчики не выполняют блокирующие сетевые/БД операции в event loop: использовать асинхронные клиенты и драйвер БД либо явно выносить блокирующую работу. CPU-тяжёлый разбор выполняется вне HTTP-пути.

### 14.2. Главный экран

Верхняя строка: три выпадающих списка с поиском — **Страна → Лига → Матч**. Нижняя область — таблица матчей выбранной лиги и подробная карточка выбранного матча. Списки и таблица синхронизированы, пользователь может выбрать матч любым способом.

- Страны брать из реестра реального покрытия, не зашивать список «весь мир». Для международных турниров отдельная категория «Международные», а не произвольная страна. Отдельно обозначать соревнования без известной страны.
- После смены страны сбросить старые лигу/матч, загрузить только её лиги. После смены лиги сбросить матч и показать только её матчи в выбранном диапазоне. До выбора родителя зависимый список недоступен.
- Названия лиг при неоднозначности дополнять сезоном и категорией, например мужская/женская/молодёжная. Внутри передавать ID, а не название.
- Элемент списка матчей: дата и время, хозяева — гости, счёт либо «— : —», статус. Порядок — по времени начала, затем ID; при неизвестном времени показывать «Дата уточняется».
- Таблица: дата/время начала, хозяева, гости, счёт, статус, тайм/минута, окончание, свежесть. По умолчанию ближайшие текущие/предстоящие матчи видны без прокрутки большой истории; доступна сортировка по началу.
- Фильтры: диапазон дат, «Все / Предстоящие / Идут / Завершённые / Перенесённые / Прочие», сезон при необходимости. Окно отбора для просмотра и окно сбора явно разделить: расширение просмотра не должно незаметно расширять сбор и нагрузку.

Карточка: страна, лига, сезон, названия хозяев и гостей, время начала с часовым поясом, время окончания либо его отсутствие, статус, текущий/итоговый счёт, тайм/минута, отдельные результаты дополнительного времени и пенальти, источник, время успешного обновления, признак конфликта. Для planned-матча отсутствие счёта отображать «— : —», не 0:0.

Названия обеих команд обязательны в выпадающем списке, каждой строке таблицы и карточке. Формат: «Хозяева — Гости», счёт в том же порядке. API возвращает `home_team: {id, name}` и `away_team: {id, name}`, а не только ID. Не делать отдельный HTTP/SQL-запрос на каждую команду: получать поля вместе с выборкой матчей через join/пакетную загрузку. При отсутствующем имени показывать «Команда не указана источником» и диагностическую отметку; не выдумывать имя. Сохранять Unicode и официальное имя; перевод необязателен. HTML экранировать, имена из источника не вставлять через небезопасный innerHTML. Длинные имена доступны полностью в карточке и подсказке, порядок хозяева/гости сохраняется.

### 14.3. Текущая игра, тайм и время окончания

| Данные источника | Отображение |
|---|---|
| Первый тайм, минута 37 | «Идёт · 1-й тайм · 37′» |
| Компенсированное время первого тайма | «Идёт · 1-й тайм · 45+2′», только если источник явно передал эти значения |
| Перерыв | «Перерыв», минута не продолжает увеличиваться |
| Второй тайм | «Идёт · 2-й тайм · 68′» |
| Дополнительное время | «Идёт · Доп. время, 1-й/2-й тайм»; минута при наличии |
| Серия пенальти | «Серия пенальти», счёт серии отдельно |
| Игра идёт, минута/тайм отсутствуют | «Идёт · минута и тайм недоступны» либо отдельное обозначение отсутствующего поля |
| Завершено, точное окончание известно | «Завершён», дата/время окончания |
| Завершено, точное окончание неизвестно | «Завершён · время окончания не предоставлено»; отдельно «Завершение обнаружено в …» |
| Отмена/перенос/приостановка | Явное название состояния, без выдуманного времени окончания |

Вычислять минуту по разнице текущего времени и kickoff запрещено: перерывы, паузы, задержки и дополнительное время делают такой таймер недостоверным. Минута — последнее наблюдение источника, а не непрерывный секундомер. Из kickoff+120 минут нельзя получать отображаемую дату окончания. Старое значение минуты сохраняется с отметкой задержки; при недоступности сети писать «Последние данные: …», не утверждать, что матч прямо сейчас идёт.

### 14.4. Расширение данных и сбора

В Match добавить nullable-поля `period` (pre_match/first_half/half_time/second_half/extra_first_half/extra_break/extra_second_half/penalties/finished/unknown), `elapsed_minutes`, `added_minutes`, `clock_observed_at`, `live_score_home`, `live_score_away`. Текущий счёт не подменяет Result, который отражает подтверждённый финал. Адаптер описывает смысл минут: общая минута матча или относительная минута периода; нормализовать только при известном соглашении. Не угадывать тайм по одной минуте. Значения, которые источник не предоставляет, остаются null.

В Coverage добавить `live_status_supported`, `live_score_supported`, `period_supported`, `minute_supported`, `observed_live_delay_seconds` (nullable). GUI показывает «Live ограничен» для источника без этих полей. Наличие финальных результатов не является доказательством live-покрытия.

Для источников с live-данными опрашивать общий список активных матчей с желаемым интервалом 120 секунд, только в пределах лимитов. Добавить `live_interval_seconds: 120` в schedule. Планировщик учитывает ожидаемые активные матчи уже от kickoff, а не только после предполагаемого окончания; при отсутствии live-возможностей оставляет прежний режим получения итогов. Внешний опрос live — отдельная группа задач; публикация финала/retention имеет приоритет. Адаптивное замедление для ожидания итогов не применяется к подтверждённой активно идущей игре с доступным live-источником: её интервал определяется live-планом и квотой.

Допускается более редкий эффективный интервал, который виден в coverage-report и GUI. В бесплатном режиме обещание минуты в реальном времени для всех лиг запрещено. Отображение live-состояний и nullable-полей обязательно; реальное получение минуты/тайма — проверяемая возможность отдельных источников, а не условие покупки доступа.

### 14.5. Обновление и пользовательские настройки

GUI обновляет данные из локальной БД через API каждые 15 секунд по умолчанию; кнопка «Обновить» выполняет такое же чтение. Это не частота обращений к сайтам. Дополнительная команда «Проверить источник» может лишь поставить объединённое задание с соблюдением лимитов, без обхода cooldown.

В интерфейсе доступны выбор часового пояса, горизонт сбора, интервалы расписания/live/итогов, окна работы, включение поддерживаемых лиг. Ввод валидируется; слишком частые запросы не обходят пределы источника. После сохранения показать, когда настройки применятся; корректно перезапустить собственный worker при необходимости. Политика 72 часов остаётся фиксированной. Сохранять пользовательские настройки и последний выбор; при исчезновении выбранной записи безопасно сбрасывать её.

Показывать загрузку, «Матчей в диапазоне нет», «Источник недоступен», «Нет подтверждённого покрытия» как разные состояния. В статусной строке — доступность backend, время последнего чтения и свежесть источника. Цвет дополняется текстом. Сеть/источник не скрывает ещё действующие данные; истёкшие матчи исключаются даже из локального кэша GUI. При удалении выбранного матча карточка очищается и сообщает об истечении хранения. После пробуждения ПК сначала пересчитывать срок хранения.

В API соревнований добавить фильтр страны; для GUI добавить `GET /api/v1/countries` с ID/названием/числом поддерживаемых лиг и категориями international/unknown. Фильтры matches принимают ID лиги/сезона. Ответы поддерживают страницу/курсор для большого числа матчей; GUI не ограничивается первыми 200 строками без возможности следующей страницы. При быстрых переключениях использовать номер UI-запроса: запоздавший ответ старой страны/лиги не перезаписывает новый выбор.

### 14.6. Приёмка GUI

1. После документированной установки сервер запускается одной командой/скриптом, веб-интерфейс открывается по указанному URL в браузере; нет обязательных платных служб и настольного GUI.
2. Выбор страны ограничивает лиги, выбор лиги ограничивает матчи. Одноимённые команды/лиги различаются по ID; международные турниры доступны отдельно.
3. На реальных бесплатных данных видны расписание и итог; на контрактных образцах проверены 1/2 тайм, перерыв, 45+N, дополнительное время, пенальти и null-поля. Если реальные minute/period недоступны, это явно указано в coverage-report.
4. Для незавершённого матча окончание отсутствует; для завершённого без timestamp показано время обнаружения с правильной подписью, без подмены фактического окончания.
5. Окно не зависает при timeout, медленном API или ошибке backend. Быстрое переключение списков не смешивает данные разных лиг.
6. «Обновить» и автопроверка GUI не вызывают дополнительные запросы к внешним сайтам. Настройки частоты не обходят лимиты.
7. Истёкший матч исчезает на следующем UI-обновлении, даже при отключении backend; карточка и локальный кэш очищаются.
8. Настройки и выбор сохраняются после перезапуска, фильтры/пагинация работают; названия обеих команд читаемы в списке, таблице и карточке. Проверка viewport 1280×720 и 390×844 без перекрытий; на узком экране таблица допускает горизонтальную прокрутку, карточка адаптируется.

В поставку добавить HTML-шаблоны, CSS/JS, скрипт запуска, инструкцию и скриншоты основных состояний. Работающий веб-интерфейс обязателен уже в 1.0.

### 14.7. Лёгкость, скорость и безопасность веб-интерфейса

- Backend и worker реализуются на Python. Переписывание на другой язык не требуется; сначала измерять сетевое ожидание, SQL, CPU и память.
- Основные HTML/CSS/JS для первого экрана суммарно не более 200 KB в сжатом виде, без необязательных изображений. Не загружать внешние шрифты, CDN, аналитические скрипты, логотипы команд или тяжёлые UI-библиотеки по умолчанию. Логотип не заменяет название команды.
- На нагрузочном профиле раздела 9: API списка со всеми названиями команд p95 ≤ 500 мс; первый экран с доступной БД на localhost ≤ 2 секунд, смена лиги до отображения до 100 матчей p95 ≤ 700 мс. Для браузера указать машину, версию, сценарий, cold/warm-cache; пять прогонов первого экрана и не менее 100 смен лиги для p95. Скорость внешнего источника не входит в скорость чтения уже сохранённых матчей.
- Страницы и запросы ограничены пагинацией; не рендерить 100 000 DOM-строк. Обновлять изменённые поля без сброса фильтров, фокуса и прокрутки. Опрос API каждые 15 секунд выполняется без наложения запросов; в скрытой вкладке приостанавливается, при возвращении возобновляется с проверкой expires_at. Ошибки чтения вызывают backoff.
- Индексированные запросы, отсутствие N+1, ограничения concurrency и повторное использование соединений обязательны. Кэшировать справочники стран/лиг, но не оставлять истёкшие матчи доступными. Локальный интерфейс работает без доступа браузера в интернет при запущенном backend и наличии сохранённых данных.
- Статические файлы версионировать; кеширование ответов матчей согласовать с expires_at. Не сохранять матчи в долговечный browser storage; хранить там только фильтры/настройки вида. Сервер валидирует настройки и ID, а не доверяет браузеру.
- Для сохранения настроек добавить документированный write-endpoint с проверкой origin/CSRF и запретом произвольных URL источников. По умолчанию администрирование только локальное; публикация в сети требует аутентификации и HTTPS. Не включать permissive CORS.
- Проверки: браузерный сквозной тест цепочки страна → лига → матч; отсутствие лишних запросов к командам/источникам; безопасный вывод имени с HTML-символами; фильтры и удаление по сроку; измерение размера ресурсов и указанного времени отклика. Результаты приложить к приёмке 1.0.

## 15. Реализация 0.7.0 и актуальный локальный профиль

06.10.2026 реализован сервис, исходники в `fast_parser`, автоматические проверки в `tests`/`scripts`, руководство в [USER_GUIDE.md](USER_GUIDE.md). Результаты и ограничения проверки: [VERIFICATION_REPORT.md](VERIFICATION_REPORT.md). Версия 1.0 остаётся целью, не заявляется завершённой.

Для локальной 0.7.0 этот раздел имеет приоритет над первоначальными архитектурными рекомендациями выше; невыполненные целевые требования явно сохраняются в роадмэпе.

### Принятые решения

- Python 3.14.6, создана `.venv`; минимальная версия исходников 3.13. Lock-файл `requirements.lock`. Исполнение без API нейросетей.
- FastAPI, Jinja2, локальные CSS/JS, асинхронный HTTP-сбор. Синхронные SQLite-операции выполняются в потоках вне event loop; внешний сбор не вызывается чтением API.
- SQLite WAL вместо PostgreSQL для запуска на имеющемся ПК без отдельного сервера/контейнера БД. Короткие транзакции, индексы, схема `PRAGMA user_version=1`, задания как `next_poll` соревнований/`html_due` дат, lease единственного активного collector. PostgreSQL/Alembic и распределённые workers не входят в готовую поставку 0.7.0. Они потребуются при подтверждённой необходимости дальнейшего масштабирования.
- Config хранится в SQLite, меняется через валидируемый API и web UI. YAML из раздела 3 — исходный пример, не фактический вход приложения; фактические поля описаны `Settings` и OpenAPI. Поддержаны оба режима диапазона и часы работы, hot apply после текущего запроса.
- Реальные источники: OpenLigaDB JSON и экспериментальные HTML-карточки Sky Sports. Паспорт и проверенный контракт: [SOURCES.md](SOURCES.md). HTML включён по умолчанию общими страницами дат; выбор отдельных лиг относится к OpenLigaDB.
- Собственные пределы с резервом: запрос к OpenLigaDB раз в 12,5 секунды, Sky HTML раз в 20 секунд. Состояния cooldown/block/lease сохраняются в БД. Источник без контракта не считается безлимитным.
- Результат одного источника помечен `verification=single_source`, `result_verified=false` означает отсутствие независимого подтверждения, а не автоматическую ошибочность итога. Финальность подтверждается status отдельно.
- По умолчанию окно 3 дня назад / 7 вперёд. Обычный исторический импорт старше 3 дней запрещён. Маркеры ID живут 180 дней после последнего наблюдения; выбранное ограничение импорта предотвращает восстановление давно удалённых матчей без точного finished_at.
- API скрывает истёкшее сразу, worker удаляет до 1 000 записей за цикл, проверяя очистку раз в 5 секунд. Полные исходные HTTP-ответы не сохраняются; карантин хранит диагностическую причину. QA-скриншоты реальных матчей удаляются через 72 часа при работающем worker.
- Localhost по умолчанию, TrustedHost, проверка Origin и CSRF на изменениях, CSP, экранирование имён. Публикация в интернете не является готовым сценарием.

### Что ещё не соответствует полному целевому ТЗ

Автоматическое сопоставление/резервирование между источниками, таблицы aliases/conflicts, независимое подтверждение результатов, эталонный мировой реестр и полная сверка покрытия не реализованы. UI даёт выбрать источник отдельно, это не fallback одного матча.

План сбора пока оценивает минимальный обход включённых лиг и внутренние лимиты, не гарантирует effective interval каждой лиги на пиковом дне. Отдельной квоты источника в сутки нет, пока она не установлена документацией. Retry реализован перепланированием и постоянным circuit breaker; отдельный счётчик четырёх попыток конкретного задания ещё требуется. Conditional requests, детектор падения числа матчей на 80%, полный набор метрик/алертов и возраст unresolved >24 часов — следующие задачи.

Настройка стран — эвристика известных кодов/названий, неопределённые лиги остаются отдельной категорией. Минута и перерыв доступны у части HTML-карточек; время конца неизвестно у обоих источников. Необязательные поля сохраняются null. Соотношение основного/дополнительного времени/пенальти не угадывается.

Семидневный пилот, отдельный профиль 2 vCPU / 4 GB, проверка Linux/Docker и переносимость установки пока не подтверждены. Автообновление UI возвращает первую страницу матчей; сохранение всех загруженных страниц запланировано. Изменения этой редакции основаны на фактической реализации, риски не объявляются закрытыми без проверок.

1.4.0 (06.10.2026): добавлены локальный профиль 0.7.0, фактические источники, решение SQLite, руководство, отчёт и явные остаточные задачи.

## 16. Требования и реализация 0.8.0

Этот раздел уточняет текущий профиль поверх раздела 15.

- Финальный статус не заменяется нефинальным без явно более новой версии источника.
  Оба ответа должны иметь `source_updated_at`; его отсутствие не считается подтверждением.
  Такие отклонения пишутся в audit только как ID. Повторная проверка или более позднее
  точное время окончания не продлевают уже установленный срок хранения.
- Сохраненные незавершенные матчи OpenLigaDB включаются в обработку полного ответа сезона
  независимо от окна. Для HTML добавляются даты ранее сохраненных игр без результата более
  24 часов. Новые старые матчи массово не импортируются. Если источник удалил игру со своей
  страницы, результат не выдумывается; такая игра остается в unresolved.
- Источники работают отдельными задачами, максимум одна задача на источник. Лимиты/cooldown
  сохраняются. Общий сетевой deadline — 30 секунд, лимит тела — 5 MB. Основной цикл обновляет
  lease каждую секунду; при потере lease/ошибке управления активные запросы отменяются.
- Актуальность карточки вычисляется из последнего принятого наблюдения, статуса, настроенных
  интервалов и состояния источника. API не гарантирует независимую достоверность результата.
- Для интеграции используется `/api/v1/changes` с монотонным числовым `seq`, вместо курсора
  только по `updated_since`: несколько изменений в одну секунду не теряются. Журнал хранит
  ID/время/тип семь дней; карточка возвращается актуальная. Payload истории не сохраняется.
  Истекший курсор дает HTTP 410. Потребитель обязан соблюдать `expires_at` локально.
- SQLite v1 → v2 добавляет журнал и индекс; перед переходом создается онлайн-копия средствами
  SQLite backup API. Неизвестная новая схема отклоняется. Копия удаляется worker через 72 часа
  после создания; без работающего worker автоматической физической очистки нет.
- Настройки включают последний сезон shortcut. Автообновление UI сохраняет загруженный объем
  страниц; смена фильтра начинает заново. Пагинация списка не является транзакционным снимком:
  для надежной начальной синхронизации применяется watermark + догрузка изменений.

Остаточные требования: подробный attempt budget/план свежести по каждой лиге, контроль gaps,
контрактные HTML-образцы, проверка восстановления копии, покрытие/aliases/fallback, недельный
пилот и ограниченный нагрузочный профиль. Это задачи 0.8.1–1.0, не заявленные гарантии 0.8.0.

## 17. Покрытие и пометки верификации 0.8.1

Текущее покрытие не сокращается ради верификации или пилота. Все найденные страны,
лиги и матчи доступны в прежнем режиме. Верификация выполняется постепенно параллельно
эксплуатации; новые лиги добавляются по мере появления доступных бесплатных источников.
Платные API и обязательные платные сервисы исключены.

UI отображает пометку для конкретной лиги, сезона и источника: «Не верифицировано»,
«Частично верифицировано», «Верифицировано». Последняя требует сверки расписания и
результатов; live проверяется отдельно. Для положительной пометки обязательны проверенный
период/выборка и основание. Пометка не подтверждает весь сезон вне указанной выборки.

Успешный сбор и актуальность карточки показываются независимо. Внутреннее legacy-поле
`state=verified` означает валидную выборку и сохраняется для совместимости; пометка
покрытия находится в `coverage_verification`, состояние сбора — в `collection_state`.
Каталог и сборщик никогда автоматически не повышают статус проверки. Пометки обновляются
оператором через защищенную форму/API после сверки. Ошибка сети не стирает выполненную
сверку; новый источник/сезон начинает непроверенным. Статус можно понизить с замечанием.

SQLite v3 добавляет отдельную таблицу пометок; v1/v2 обновляются с копией соответствующей
версии, без удаления текущего каталога. Остаточная эксплуатационная диагностика перенесена
в 0.8.2. Новые бесплатные адаптеры подключаются по одному; пометки новых лиг не ограничивают
